Beginner guide: build your first spatial IW world

You do not need to understand IW’s internal JSON first. The easiest path is to let an authoring-capable AI assemble the full world, then review and test it.

Part A — Prepare the idea

  1. Write a short game brief. Include the premise, player role, tone, content boundaries, important activities, and whether the story is ongoing or has an ending.
  2. List the first map essentials. Name the starting place, two or three nearby places, the first political region, major terrain, and at least one road or waterway.
  3. Choose a rough origin. Put (0.00, 0.00) southwest of the playable area. X increases east and Y increases north. Exact real-world surveying is unnecessary.

Part B — Use the easiest AI-assisted workflow

  1. Give the AI the IW Builder full-package.zip and this Spatial Context package.
  2. Ask it to read Authoring-Prompt.md, customize the two spatial YAML files, compile the bank, merge its components into a complete world, and validate the final export.
  3. Review the proposed map origin, stable IDs, area containment and water direction. Correct concepts now; coordinates can remain approximate.
  4. Keep the returned complete world JSON and customized spatial package together. The JSON runs the world; the YAML remains your editable map source.

Part C — Edit the map in a dependable order

  1. Areas first: draw simplified polygons in world-geography.yaml, then give them meaning under areas: in world-spatial.yaml.
  2. Named places: write each place under locations:, then add its coordinates under location_points: using the same ID.
  3. Linear features: add roads, trails and waterways under paths:. Always set type.
  4. Water direction: order every river, creek and stream from upstream to downstream. Elevation should normally fall along the sequence.
  5. Relationships: use path_ids only for exact named intersections. Area membership and nearby locations are calculated from coordinates.
  6. Starting state: give initial_navigation authoritative XYZ coordinates, an optional location anchor and an optional active segment.
  7. Compile: run python tools/build_spatial_context.py. Fix errors; read warnings rather than ignoring them.

Part D — Put the world into Infinite Worlds

  1. Start from World-Template.json or export an existing world.
  2. Merge every compiled bank component into that complete JSON. An AI can do this; do not paste the bank itself into IW.
  3. In the IW editor, enable optional features, advanced/miscellaneous features if needed, and raw JSON.
  4. Export a backup. Import replaces the whole base-world definition.
  5. Paste the complete merged JSON without Markdown fences or a blank line after the final brace. Choose Import JSON to world and save.
  6. Start a new playthrough. Existing live copies do not inherit later edits to the base world.

Why locations and areas share one source

QuestionRC3 answer
Does one source increase model cost?No. The source is compiled into hidden trackers; only Spatial Local Context is AI-visible.
Does PawScript parse one large combined catalog?No. The compiler splits locations and areas into separate runtime tracker values.
What becomes easier?One semantic resource file, one metadata header and simpler authoring handoff.
What becomes riskier?A YAML syntax or duplicate-key error can block both catalogs. The compiler catches this before integration.
What about enormous worlds?Eventually shard by region; IW’s maximum practical hidden-tracker size has not been established.

Design boundary: merge the source, not the runtime responsibilities. This keeps authoring convenient without making every runtime read larger.

Metric 3D coordinates

x_kmKilometres east of the map origin.
y_kmKilometres north of the map origin.
z_mMetres above the chosen elevation datum.
PrecisionTwo XY decimals equal roughly 10 metres.

Store calculations in metric even if the setting presents miles or leagues. Approximate coordinates are usually more useful than false cartographic precision.

Free roaming: coordinates first

The player no longer has to be “at Bramble Gate” or “on segment 2 of the King’s Road.” XYZ coordinates are always authoritative; named places and path progress are optional relationships.

Absolute positionx_km, y_km and z_m are required.
Location anchorOptional, and accepted only when it falls within the configured tolerance.
Active pathOptional. Use it for path-locked progress, grade and waypoints.
Nearby pathsFound automatically even when the player crosses or follows beside one.

What refresh derives

OutputHow it is resolved
current_areasBounding-box prefilter followed by exact polygon and hole tests.
nearby_locationsSparse-grid candidates, discovery state, exact distance, nearest-first limit.
nearby_pathsProjection onto candidate path segments and exact perpendicular distance.
current_locationOnly a valid in-tolerance location_anchor.

Query settings

query_settings:
  index_cell_km: 10.0
  nearby_location_radius_km: 15.0
  nearby_path_radius_km: 2.0
  on_path_tolerance_km: 0.05
  max_nearby_locations: 5
  max_nearby_paths: 3
  location_anchor_tolerance_km: 0.10

The cell size controls candidate indexing, not map precision. Exact distances and polygon tests still use the full coordinates.

Movement ownership: the package calculates context from coordinates; it does not decide that prose such as “I walk north for an hour” has committed a particular position. Host-world logic must write the authoritative coordinates before refresh.

Location points and typed paths

Location point
location_points:
  stone_bridge:
    x_km: 41.80
    y_km: 24.40
    z_m: 263
    path_ids: [kings_road, river_vey]
    # Areas and nearby places are coordinate-derived.
Road path
paths:
  kings_road:
    name: King's Road
    type: road
    class: major_maintained
    surface: fitted_stone_and_gravel
    directionality: bidirectional
    nav_points:
      - id: kings_road_001
        x_km: 28.00
        y_km: 14.00
        z_m: 140
        cumulative_km: 0.00
        location_id: southwatch_post
        role: checkpoint
River path
paths:
  river_vey:
    name: River Vey
    type: river
    class: perennial
    navigability: shallow_boats_below_stone_bridge
    nav_points:
      # Ordered upstream to downstream
      - {id: river_vey_001, x_km: 52.00, y_km: 34.00, z_m: 420, cumulative_km: 0.00}
      - {id: river_vey_002, x_km: 45.50, y_km: 28.50, z_m: 318, cumulative_km: 8.51}

For a natural water path, index order is flow direction. Forward means downstream; reverse means upstream.

One semantic source, two collections

spatial_context:
  package_version: "1.0.RC3"
  schema_version: "1.2"
  data_role: spatial

locations:
  bramble_gate:
    name: Bramble Gate
    kind: checkpoint
    summary: A guarded roadside inn and customs post.
    initial_state:
      discovered: true
      visited: true

areas:
  northern_crown:
    name: Northern Crown
    layer: political
    kind: kingdom
    geometry: northern_crown_extent
    summary: A hereditary kingdom controlling the northern roads.
    contains: [duchy_of_vey]

contains is semantic nesting, not subtraction. A lake is still in its continent; a duchy is still in its kingdom. Geometry holes are reserved for actual excluded space.

Manual integration details

  1. Compile the two YAML sources.
  2. Open a complete IW export and the compiled data bank.
  3. Insert all six trackers, the instruction block and the refresh trigger into their native arrays.
  4. Resolve native-ID collisions consistently.
  5. Preserve the six tracker variableName values or rewrite every dependent script reference.
  6. Give one host mechanism ownership of XYZ updates, and commit them before refresh when same-pass data is needed.
  7. Validate the complete world, not only the bank.
  8. Test a named location, free-roam coordinate, road-adjacent point, area boundary and active river in Sandbox and then in a new playthrough.

Importing raw JSON replaces the complete base-world definition. Export a backup first.

RC3 boundaries

  • The host supplies elevation; no digital elevation model is interpolated.
  • Path proximity does not perform route finding or river-network traversal.
  • Area membership is 2D; elevation does not change polygon membership.
  • The host world owns authoritative coordinate changes and optional path progress.
  • Practical maximum hidden-tracker size is not established.
